# M7 reference comparison — 2026-09-01

This comparison is a scope and architecture comparison, not a general product
ranking. OSS capabilities are separated from hosted or commercial features.
The common target is PostgreSQL, but postgresem remains the only evaluated
engine whose supported execution contract requires PostgreSQL to enforce the
final GRANT/RLS decision.

## Decisions

**Adopt now**

- One-way Apache Ossie import as a reviewable candidate, with PostgreSQL catalog
  evidence resolving physical type, nullability, PK, FK, and visibility.
- Fingerprinted catalog drift reporting with GRANT/RLS/constraint changes
  treated as breaking.
- Structured conversion issues and warnings; no silent fallback to generic
  types, prose metrics, or a full external manifest.

**Defer**

- Explicit fan-out-safe aggregation anchors, modeled after Malloy aggregate
  locality and Cube multiplied-measure planning, to M8.
- Time spines, cumulative/derived metrics, and custom calendar tables, using
  MetricFlow and Cube as semantic references, to M8.
- Same-PostgreSQL pre-aggregation, closer to Publisher persistence than a
  mandatory second datastore, to M10.
- PostgreSQL wire serving until an ADR can preserve the no-raw-SQL boundary.

**Reject intentionally**

- Caller-asserted identity or session attributes as the final authorization
  source.
- Unauthenticated remote MCP.
- External semantic files as a live runtime authority.
- Multi-dialect execution, arbitrary imported SQL expressions, and silent
  lossy conversion.
- Mandatory cache, vector, or secondary metadata infrastructure.

## Differentiated position

postgresem does not attempt to replace the GenBI workflow, broad APIs, modeling
language expressiveness, or cache systems of the references. It is the narrow
gateway for teams that want meaning, revision history, query/write contracts,
identity enforcement, and audit evidence to stay inside the same PostgreSQL
operational boundary as the data.

That position is strongest where the references are weakest or intentionally
out of scope: immutable in-database publication, database-enforced RLS
principal propagation, a no-raw-SQL agent contract, governed insert/upsert, and
catalog drift that treats authorization metadata as first-class evidence.

The runtime comparison is deliberately not a claim that equal aggregate output
means equal governance. Wren executes this task through a raw SQL query, Cube
through a structured service query, Malloy through its modeling/query language,
and MetricFlow through a metric request. postgresem's public runtime remains a
closed LSQ/LSM contract bound to an immutable in-database revision and a fixed
PostgreSQL principal. The reference features worth adopting are selected
without importing their SQL or authorization boundaries.

## Reproduction

Run the repository-owned subset without a database:

```sh
make test-reference-comparison
```

The pinned external runtime harnesses are in
[`tests/reference-comparison/runtime`](../../tests/reference-comparison/runtime/).
The dedicated
[`reference-comparison.yml`](../../.github/workflows/reference-comparison.yml)
workflow initializes one PostgreSQL 18 dataset, executes every reference in
isolation, checks the expected decimal result, and retains per-engine JSON
evidence. Run
[`33517361442`](https://github.com/rioriost/postgresem/actions/runs/33517361442)
passed for Wren AI, Cube Core, Malloy, and MetricFlow with
`total_revenue = 545.50`. The PostgreSQL and Cube images use immutable
digests; Python uses exact `3.12.13`, `uv 0.12.8`, and committed transitive
locks; Malloy uses Node `24.20.0` and `npm ci` against its committed lockfile.
Every evidence document records the relevant image, lock, and tool identity.

Malloy evidence uses npm `0.0.432` because the evaluated `v0.0.433` source
release did not publish matching npm artifacts. The evidence records both
versions instead of silently substituting one. Product capability rows remain
based on the linked release source and official documentation, and cloud-only
services are not counted as OSS behavior.
