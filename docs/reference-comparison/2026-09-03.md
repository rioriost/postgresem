## Findings applied in M10

### Scale

Cube and MetricFlow demonstrate the value of explicit operational surfaces for
cache or export state, but the postgresem baseline did not identify guarded
query execution as the first bottleneck. The measured problem was catalog
introspection issuing relation-detail queries repeatedly. M10 therefore
replaced those N+1 paths with set-based PostgreSQL scans and reduced the
1,000-relation Apple Container reference run from roughly 2.1 seconds to
105–134 milliseconds.

No connection pool, prepared-plan cache, result cache, materialized-view
router, or pre-aggregation scheduler was added without measurement evidence.

### Authoring

The references use file-oriented languages or manifests that scale through
composition, code review, and generators. postgresem keeps PostgreSQL as the
authoritative evidence source and adds a deterministic scaffold rather than a
second live model authority. It infers only direct supported fields, validated
single-column keys, temporal roles, and a safe row-count candidate. Business
metrics, relationships, writes, and publication still require review.

### Operations and recovery

Cube and MetricFlow expose dedicated service APIs. postgresem instead adds one
fixed `SECURITY DEFINER` PostgreSQL report executable only by the audit role.
It reports aggregate catalog, semantic, audit, capacity, migration, lock, and
materialized-view state without exposing requests, SQL, rows, identities, or
object names.

The Apple Container upgrade reference requires a verified backup that matches
the live pre-upgrade migration and published-revision manifests, blocks on
incomplete audit rows, applies forward migrations, preserves published hashes,
and runs a guarded canary plus the operational report. Production rollout,
backup retention, RPO/RTO, and rollback remain platform-operator concerns.

## Intentional non-parity

- **No automatic pre-aggregation or materialized-view routing.** Cube's
  external Cube Store and MetricFlow's scheduler-built cache/export tables
  solve broader acceleration workflows. postgresem only observes PostgreSQL
  materialized-view population state because acceleration was not the measured
  M10 bottleneck.
- **No arbitrary SQL compatibility surface.** Cube Semantic SQL, Wren query
  surfaces, and Malloy SQL/source expressiveness are not copied into the public
  contract.
- **No multi-engine abstraction.** Wren and Malloy support multiple execution
  engines, and Cube/MetricFlow target broader warehouses. postgresem remains
  PostgreSQL-only to preserve database-native type, GRANT, RLS, transaction,
  audit, and recovery semantics.
- **No second semantic source of truth.** File-oriented authoring remains useful
  for the references; postgresem scaffolds a candidate from database evidence
  but publication authority remains the immutable PostgreSQL revision.
- **No service-owned authorization substitute.** Reference access-control or
  cache contexts do not replace PostgreSQL authorization. Every postgresem
  query and mutation still reaches PostgreSQL under a fixed validated role.

These are deliberate trust-boundary choices, not missing claims of feature
equivalence.
