## Scope and methodology

Three security-review agents examined the current source at the recorded
commit, not only the changes since the earlier review. They traced
untrusted inputs to sensitive operations, checked the supported trust model
against repository instructions and accepted ADRs, inspected rejection
coverage, and ran the focused checks recorded below.

The runtime pass checked explicit application expiration/issued-at/not-before
validation rather than assuming that disabled JWT-library default expiration
validation implied a bypass. It found new database connections per operation,
not a shared session pool. Mutation authority inputs were traced to verified
identity and trusted configuration; service-internal database helper powers
were not treated as a public arbitrary-SQL interface.

The compiler/database pass found typed rendering and bound values, strict
publication loading with revision verification, read-only catalog-bound OSI
projection, and qualified privileged helpers with fixed search paths and
explicit grants. The demo/distribution pass found exact loopback Host and
POST Origin handling, closed schemas, text-only DOM rendering, and all 26
workflow action references pinned to full commit identifiers.

These are source-inspection conclusions, not substitutes for live database,
proxy, browser, or release-artifact exercises. The demo review assumes the
documented local, fictional-data, trusted-operator deployment.

### Reconciliation contract clarification

The cross-boundary review found that current `principal-v1` reconciliation
binds the stable authority ID, but does not additionally compare the stored
writer role (`mutation_executor.rs:461-488` and
`migrations/0009_mutation_reconcile_precedence.sql:18-40`). The role-bearing
hash applies to the legacy lookup branch. An identity retaining its stable
authority ID and current mutation permission can therefore retrieve its own
historical mutation metadata after an operator remaps its writer role.
Only identifiers, status, counts, and timestamps are returned, not result
rows or mutation values. Claim/replay separately checks the stored writer
role (`migrations/0008_mutation_authority_idempotency.sql:204-214`).

This differs from ADR 0015's same-writer-role reconciliation statement and
remains a contract-alignment question for maintainers. No significant
exploitable disclosure or replay authorization bypass was established.
This record does not claim that current reconciliation enforces a
stored-writer-role comparison.

## Dependency advisory requiring disposition

The installed `cargo-audit 0.22.1` reported:

| Field | Observation |
|---|---|
| Locked package | `time 0.3.36` |
| Source locations | `Cargo.toml:31`; `crates/postgresem/Cargo.toml:26`; `Cargo.lock:1496-1508` |
| Advisory | [RUSTSEC-2026-0009](https://rustsec.org/advisories/RUSTSEC-2026-0009.html) |
| Aliases | `CVE-2026-25727`, `GHSA-r6v5-fh4h-64xc` |
| Reported impact | Stack exhaustion during RFC2822 parsing; denial of service |
| Patched range | `>=0.3.47` |
| Application reachability | No attacker-controlled call path to RFC2822 parsing identified in the inspected runtime; source-level assessment, not an exhaustive binary proof |
| Disposition | Not fixed or accepted by this review; update the direct version pin and lockfile through the normal compatibility process, then repeat the audit with current advisory data |

The package is a direct dependency and is also reached through
`jsonwebtoken 9.3.1 -> simple_asn1 0.6.3 -> time 0.3.36`; the parsing feature
is enabled. Inspection of the local cached dependency sources found that
`simple_asn1` parses ASN.1 dates with fixed numeric format descriptions,
not RFC2822. Production authentication loads operator-controlled JWKs via
`DecodingKey::from_jwk` (`mcp_http_auth.rs:1102`), not the PEM/ASN.1 loader.
JWT claims are decoded as JSON, and application time claims are validated as
integers (`mcp_http_auth.rs:900-932`, `1656-1665`).

No RFC2822 call site or direct `time` parsing use was found in the repository
crates. This is the basis for the narrower reachability assessment; request
size limits are not being claimed as a fix. No stack-exhaustion probe was
run on the shared host, and future use of the affected parser would require
reassessment.

The advisory database was an existing local cache: 1,235 advisories at
commit `72f8b23d78ea6c4c9ded301a4c6ec4260e8b4c27`, dated
`2026-09-01T09:55:13+02:00`. It was not refreshed. This audit therefore does
not establish coverage through the review date. No new audit tool was
installed, and dependency contents were not uploaded for scanning.

The lockfile inspection found 215 packages: 213 checksummed crates.io
registry entries and two workspace packages, with no alternate source
origins. Checksums and action pins are provenance controls, not proof that
dependencies or actions are vulnerability-free.

No real MCP/OpenAI end-to-end flow, Playwright browser run, container
deployment, release workflow execution, or fresh published-artifact signature
verification was performed. Container files were source-reviewed, but no
container image or OS/Cosign binary was vulnerability-scanned. No deployed
image digest or operational 28-day pilot evidence is inferred.

This evidence supports continued qualification within the inspected scope,
not an unconditional release approval. Dependency-advisory disposition and
the existing external-evidence gates remain explicit.

### Corrections

- **Dependency advisory:** Removed the unused direct `time` dependency and
  disabled jsonwebtoken's unused default PEM feature. The resolved graph no
  longer contains `time` or `simple_asn1`; the supported JWK authentication
  path and declared Rust MSRV are unchanged. This removes the affected
  component rather than accepting its residual risk.
- **Writer-role reconciliation:** Added forward migration 0011 and bound the
  internal lookup's fifth parameter to trusted executor configuration across
  CLI, stdio, and HTTP. The selected principal-v1 row is checked before any
  legacy fallback could occur. A mismatched role returns no state; matching
  legacy-only lookup and stable identity after HMAC rotation remain supported.
  The old unguarded overload is removed. Existing migrations, table grants,
  and PostgreSQL RLS enforcement are not weakened.
